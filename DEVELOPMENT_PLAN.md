# План развития MindVault

**От прототипа захвата мыслей — к личному ИИ-компаньону: вторая память, штурман планирования, зеркало состояний.**

---

## 1. Видение и текущее состояние

### 1.1. Видение

MindVault превращает смартфон в личного компаньона, который:

- **Помнит за пользователя.** Каждая записанная мысль становится частью долговременной семантической памяти. Компаньон отвечает на вопросы вида «что я думал про ремонт в марте?» и сам замечает, что одна и та же мысль возвращается снова и снова.
- **Понимает тенденции планирования.** Превращает сырые мысли в задачи и планы, видит паттерны откладывания, помогает приоритизировать с учётом реального состояния человека, а не только списка дел.
- **Анализирует состояния в нескольких слоях.** Энергия, настроение, фокус — через быстрые чек-ины и пассивные сигналы из самих записей. Со временем компаньон показывает тренды и корреляции, которые человек сам про себя не замечает.
- **Предлагает редкие функции,** которых нет в типичных заметочниках и таск-менеджерах: «Эхо мыслей», «Анти-список», «Капсула времени» и другие.

Принципиальная позиция продукта — **приватность по умолчанию**: все данные пользователя живут на его устройстве, а облако используется только как «арендованный мозг» для LLM-вычислений, без хранения чего-либо.

### 1.2. Текущее состояние (v0.1)

Сегодня MindVault — это PWA-прототип: один `index.html` (~1030 строк HTML + CSS + JS), `manifest.json`, простой `sw.js` и WebView-обёртка в `android/` (подписанный debug-ключом APK, targetSdk 23).

**Что уже работает:**

- быстрый захват мыслей (текст + голосовой ввод через Web Speech API);
- автокатегоризация по 6 категориям на ключевых словах;
- список с поиском и фильтрами-чипами, отметка «выполнено», удаление долгим нажатием;
- статистика (закрыто за неделю, активные, добавлено сегодня, разбивка по категориям);
- баннер-напоминание при открытии после заданного времени;
- экспорт в JSON; хранение в `localStorage`.

**Ключевые ограничения, которые снимает этот план:**

| Ограничение | Последствие |
|---|---|
| Монолитный файл на 1000+ строк, ванильный JS | Любая новая фича удорожает следующую; рост техдолга |
| `localStorage` | Лимит ~5 МБ, нет индексов, нет места для эмбеддингов |
| Категоризация по ключевым словам | Хрупкая, не понимает смысла |
| Нет редактирования мысли, undo, тёмной темы | Базовый UX ниже ожиданий пользователя в 2026 году |
| Напоминание — только баннер при открытии | Нет настоящих запланированных уведомлений |
| WebView-обёртка, targetSdk 23 | Непригодна для публикации в RuStore |

## 2. Целевая архитектура

Архитектура строится вокруг одного принципа: **local-first**. Устройство — единственный источник правды для данных пользователя; сервер — тонкий stateless-прокси к LLM. Такой расклад одновременно решает три задачи: приватность (мысли не покидают телефон, кроме текста конкретного запроса), стоимость (нет серверной базы, бэкапов, аккаунтов) и скорость разработки (90% логики — на клиенте).

```
┌─────────────────────────── Телефон ───────────────────────────┐
│  PWA (Vite + TypeScript)                                       │
│  ├─ components/  UI-слой                                       │
│  ├─ stores/      реактивное состояние                          │
│  ├─ services/    IndexedDB, поиск, RAG-сборка, нотификации     │
│  └─ IndexedDB:   мысли, чек-ины, задачи, ЭМБЕДДИНГИ, summary   │
│  Capacitor-обёртка: scheduled notifications, SpeechRecognizer  │
└──────────────────────┬─────────────────────────────────────────┘
                       │ HTTPS (только текст запроса)
┌──────────────────────▼─────────────────────────────────────────┐
│  Бэкенд-прокси (FastAPI, stateless)                             │
│  /embeddings /categorize /chat /summarize /tone                 │
│  → OpenAI-совместимые провайдеры (Groq / VseGPT / DeepSeek)     │
└─────────────────────────────────────────────────────────────────┘
```

### 2.1. Клиент: Vite + TypeScript с первого этапа

Прототип на ванильном JS своё отработал. Дальше приложение получает чат, асинхронные LLM-вызовы, несколько хранилищ и фоновые задачи — без типизации и модульности это превратится в неподдерживаемый клубок уже к Этапу 2. Поэтому первым делом проект переводится на **Vite + TypeScript** с ESLint/Prettier и трёхслойной структурой:

- `services/` — работа с IndexedDB, API-клиент прокси, семантический поиск, планировщик уведомлений;
- `stores/` — реактивное состояние (лёгкие сигналы/observable без тяжёлого фреймворка);
- `components/` — UI-компоненты, собранные из существующей вёрстки (текущие CSS и разметка переиспользуются — UX прототипа уже проверен).

Хранилище переезжает с `localStorage` на **IndexedDB** с версионированием схемы: каждая версия БД имеет номер, апгрейд выполняется миграционным скриптом в обработчике `onupgradeneeded`, и перед любой миграцией автоматически создаётся backup (полный JSON-дамп в отдельном store + предложение скачать файл). Приложение остаётся офлайн-first: все функции, кроме ИИ, работают без сети; `sw.js` обновляется до полноценного кэширования собранных ассетов.

### 2.2. Модель данных

Сущности проектируются сразу «на вырост» — с полями, которые понадобятся на поздних этапах, чтобы не плодить миграции. Опорные интерфейсы:

```typescript
interface Thought {
  id: string;               // uuid (вместо Date.now() из v0.1)
  text: string;
  category: string;
  tags: string[];
  createdAt: number;
  updatedAt: number;
  done: boolean;
  completedAt: number | null;
  closedAt: number | null;      // «закрыто» через Анти-список (≠ выполнено)
  embedding: number[] | null;   // вектор от прокси, хранится только локально
  tone: 'positive' | 'neutral' | 'anxious' | 'tired' | null; // LLM-анализ
  echoGroupId: string | null;   // группа «Эха мыслей»
  linkedTaskIds: string[];      // задачи, созданные из этой мысли
  source: 'text' | 'voice' | 'braindump';
}

interface StateCheckin {
  id: string;
  createdAt: number;
  energy: 1 | 2 | 3 | 4 | 5;   // физический слой
  mood: 1 | 2 | 3 | 4 | 5;     // эмоциональный слой
  focus: 1 | 2 | 3 | 4 | 5;    // ментальный слой
  note: string | null;
}

interface TimeCapsule {
  id: string;
  thoughtId: string;
  openAt: number;              // когда «вскрыть»
  notificationId: number;      // id запланированного уведомления Capacitor
  openedAt: number | null;
}
```

Аналогично описываются `Task` (шаги ИИ-декомпозиции, приоритет, дедлайн), `Echo` (группа похожих мыслей, счётчик возвратов, порог схожести) и `ProfileSummary`. Миграция из v0.1 маппит старые записи на `Thought` с заполнением новых полей значениями по умолчанию — **все существующие данные пользователя сохраняются без потерь**.

### 2.3. Семантическая память: гибридный подход

Сердце «второй памяти» — эмбеддинги, и здесь выбран гибрид облака и устройства. При создании или изменении мысли её текст отправляется на эндпоинт `/embeddings` прокси, полученный вектор сохраняется **только локально** в IndexedDB рядом с мыслью. Дальше всё происходит на устройстве: семантический поиск — это cosine similarity по локальным векторам (для тысяч мыслей линейный проход занимает миллисекунды, никакая векторная БД не нужна).

Чат-компаньон работает по RAG-пайплайну: запрос пользователя → его эмбеддинг → top-k релевантных мыслей из локального индекса → top-k + краткий summary профиля инжектятся в промпт → ответ LLM. **Summary профиля** — компактный (до ~500 токенов) портрет пользователя: активные темы, повторяющиеся заботы, динамика состояний. Он пересобирается раз в сутки при первом открытии приложения — из мыслей и чек-инов за последние 30 дней через эндпоинт `/summarize` — и хранится локально в IndexedDB до следующей пересборки.

Почему гибрид, а не крайности: полностью облачная память потребовала бы хранить мысли на сервере (ломает приватность и тянет за собой аккаунты), полностью локальные эмбеддинг-модели в WebView пока тяжелы и медленны на средних телефонах. Гибрид даёт качество облачных эмбеддингов по цене копеек за запрос, при этом поиск и сами данные никогда не покидают устройство.

### 2.4. Бэкенд-прокси: тонкий, stateless, дешёвый

Сервер — это FastAPI-приложение, построенное по образцу проверенного `llm.py` из Nailbot: универсальный OpenAI-совместимый клиент, у которого провайдер (Groq / VseGPT / DeepSeek / любой OpenAI-compat) и модель задаются через переменные окружения, причём **модель назначается per-feature** — дешёвая и быстрая для категоризации и тональности, сильная и эмпатичная для чата компаньона — с автоматическим fallback на запасную модель при ошибках основной.

Эндпоинты: `/embeddings`, `/categorize`, `/chat`, `/summarize`, `/tone`. Для категоризации, тональности и суммаризации ответы запрашиваются как **structured outputs** (JSON mode / tool calling) — это убирает хрупкий парсинг свободного текста и снижает стоимость постобработки. Прокси полностью stateless: не хранит ни мысли, ни эмбеддинги, ни историю чата (контекст каждый раз приходит с клиента). Из служебного — только rate-limit на клиентский идентификатор и **анонимизированный учёт использования LLM по фичам** (счётчики токенов на эндпоинт), чтобы видеть структуру затрат и вовремя замечать аномалии.

### 2.5. Обёртка: Capacitor

Вместо самописного WebView и чистого TWA выбирается **Capacitor**. Решающий аргумент — запланированные локальные уведомления: «Капсула времени», еженедельные сводки и утренний разбор «Разгрузки перед сном» требуют надёжного «разбудить пользователя в заданный момент», чего нет ни в PWA, ни в TWA (Web Push требует сервера и нестабилен на Android-вендорах). Плагин `@capacitor/local-notifications` решает это нативно. Бонусы: нативный `SpeechRecognizer` вместо ограниченного Web Speech API в WebView, прямой контроль targetSdk (33+ для RuStore), доступ к нативным API по мере надобности — при этом весь продуктовый код остаётся одной веб-кодовой базой.

## 3. Этапы развития

Сроки каждого этапа указаны в формате «MVP этапа + итерация полировки и тестов» — опыт показывает, что вторая половина не опциональна.

### Этап 1 — Фундамент (MVP ~1,5 недели + ~1 неделя полировки)

Цель: снять техдолг прототипа и догнать базовые ожидания от приложения, не меняя проверенный UX.

- Инициализация Vite + TypeScript, ESLint/Prettier; перенос монолита в структуру `services / stores / components` (вёрстка и стили переиспользуются).
- IndexedDB с версионированием схемы; миграция из `localStorage` с обязательным backup до миграции — **ни одна существующая мысль пользователя не теряется**.
- Capacitor-проект вместо самописного WebView; **proof-of-concept запланированных локальных уведомлений** (критичен для Этапов 5–6 — делаем рано, чтобы рано узнать о проблемах).
- Базовый UX: редактирование мысли, undo после удаления (snackbar), swipe-действия (закрыть/удалить), тёмная тема, импорт JSON (к существующему экспорту), пользовательские категории и теги.
- Каркас тестов: Vitest для сервисов (миграции — в первую очередь), Playwright smoke-тест основного потока «открыл → записал → закрыл».

### Этап 2 — ИИ-ядро (MVP ~2 недели + ~1 неделя полировки)

Цель: появляется собственно компаньон.

- Бэкенд-прокси (раздел 2.4) и API-клиент на клиенте с graceful degradation: нет сети или прокси недоступен → приложение молча работает в офлайн-режиме.
- LLM-категоризация новых мыслей с fallback на текущий keyword-словарь (офлайн и при ошибках).
- Эмбеддинги при сохранении мысли + фоновая разовая индексация архива; локальный семантический поиск (вкладка «умный поиск» рядом с обычным).
- Чат-компаньон с RAG-памятью: «что я думал про X?», «что у меня висит по здоровью?».
- **Стратегия промптов компаньона** — оформляется как отдельный артефакт: личность (спокойный, тёплый, без навязчивости), tone of voice на русском, правила работы с памятью (на что можно ссылаться, как цитировать мысли пользователя), принципы инъекции RAG-контекста (top-k, бюджет токенов, что делать при пустой выдаче).
- Еженедельная ИИ-сводка: что записано, что закрыто, что зависло.

### Этап 3 — Слои состояния (MVP ~1,5 недели + ~0,5 недели полировки)

Цель: приложение начинает «видеть» человека, а не только его задачи.

- Чек-ин за 10 секунд: три слайдера — энергия (тело), настроение (эмоции), фокус (голова); опциональная заметка.
- Пассивные сигналы — только простые и надёжные метрики: время суток и день недели записей, интервалы между записями, длина текста, тональность текста (батч-анализ через `/tone` раз в сутки). Метрики вроде «темпа набора» сознательно исключены: в PWA они сложны в реализации и сомнительны по пользе.
- Экран «Состояние»: тренды по слоям, корреляции («продуктивные записи — чаще утром», «тревожный тон растёт в конце месяца»). Корреляции показываются только при достаточном объёме данных — никаких выводов из трёх точек.

### Этап 4 — Умное планирование (MVP ~1,5 недели + ~0,5 недели полировки)

Цель: мысли начинают превращаться в результаты.

- «Мысль → план» одним тапом: ИИ-декомпозиция на конкретные шаги (structured output → `Task[]`), связь через `linkedTaskIds`.
- Приоритизация с учётом состояния: при низкой энергии компаньон предлагает лёгкие шаги, на пике фокуса — самое сложное.
- Ритуал weekly review: компаньон проводит по зависшим мыслям и предлагает каждой судьбу — план, капсула, анти-список.
- Распознавание паттернов откладывания: «эта задача переносится третью неделю — разбить на шаги или отпустить?»

### Этап 5 — Уникальные функции (~2 недели на первые три)

Функции, которых нет в типичных приложениях. **На первый публичный релиз — строго три** (защита от scope creep), остальные после релиза.

В релиз:

- **«Эхо мыслей»** — компаньон через эмбеддинги замечает, что пользователь записывает по сути одну и ту же мысль снова и снова, показывает её «вес» (сколько раз возвращалась за какой период) и предлагает наконец закрыть: сделать, запланировать или отпустить. Порог схожести настраивается, ложные срабатывания пользователь убирает вручную («это не то же самое») — и система это запоминает для группы.
- **«Анти-список»** — список того, что решено *не делать*. Компаньон помогает осознанно отпустить мысль с коротким ритуалом закрытия (почему отпускаю → подтверждение → мысль архивируется с `closedAt`). Снимает фоновую вину за «вечно висящее».
- **«Капсула времени»** — мысль отправляется себе в будущее и «вскрывается» запланированным уведомлением в заданную дату: «Письмо от тебя из июня».

После релиза:

- **«Разгрузка перед сном»** — вечерний поток сознания без структуры; утром ИИ возвращает всё разобранным по категориям и задачам.
- **«Личный летописец»** — связная «глава недели/месяца», написанная из мыслей и состояний: дневник, который пишется сам.

### Этап 6 — Публикация и монетизация (~2 недели)

- Релизная сборка Capacitor: targetSdk 33+, собственный release-ключ (хранится навсегда), современный pipeline сборки вместо `build.sh` на dx.jar.
- Публикация в RuStore.
- Freemium: захват мыслей, категории, поиск, статистика, чек-ины — бесплатно навсегда; ИИ-функции (компаньон, сводки, «Эхо», декомпозиция) — по подписке. Биллинг: RuStore Billing на клиенте + опциональная lightweight-проверка подписки на прокси (он и так стоит на пути всех ИИ-запросов — естественная точка контроля).
- Метрики с первого дня: retention D1/D7/D30, активные мысли на пользователя, доля закрытых, конверсия в подписку.

## 4. Риски и митигации

| Риск | Вероятность / влияние | Митигация |
|---|---|---|
| Взрыв затрат на LLM при росте пользователей | Средняя / высокое | Per-feature модели (дешёвые для категоризации/тональности), кэширование эмбеддингов (повторно не считаем), rate-limit на клиента, анонимизированный учёт токенов по фичам с алертами |
| Низкая точность анализа тональности на русском | Средняя / среднее | Валидация на реальных записях до включения в UI; тональность — всегда «мягкий» сигнал, не диагноз; возможность отключить в настройках |
| Ненадёжность scheduled notifications на Android (агрессивные battery-оптимизации вендоров) | Высокая / высокое для «Капсулы» | PoC на Этапе 1 — узнаём правду до того, как на уведомления завязаны фичи; fallback: in-app напоминания и баннер при открытии (как в v0.1) |
| Слабый retention в freemium | Средняя / высокое | Бесплатное ядро самодостаточно полезно; метрики с первого релиза; еженедельная сводка как возвращающий триггер |
| Scope creep уникальных функций | Высокая / среднее | Жёсткий лимит: три функции на первый релиз; остальные — только после данных о retention |

## 5. Сквозные требования качества

Действуют на каждом этапе, не «потом»:

- **Приватность:** local-first; на сервер уходит только текст конкретного запроса; опциональное шифрование экспортируемого JSON паролем.
- **Офлайн:** все не-ИИ функции работают без сети полностью.
- **Graceful degradation:** недоступность прокси никогда не блокирует пользователя — категоризация падает на ключевые слова, ИИ-кнопки честно показывают состояние «офлайн».
- **Тестирование:** Vitest на сервисы (миграции, поиск, RAG-сборка) и Playwright на ключевые потоки — в definition of done каждого этапа.
- **Производительность:** виртуальный скролл списка после ~200 записей; запросы к IndexedDB по индексам, не полным перебором (кроме cosine similarity, где линейный проход осознан и измерен).
- **i18n-каркас с Этапа 1:** все строки через словарь, даже пока язык один (русский). Дешёво сейчас — дорого потом.

## 6. Порядок и критерии готовности

| Этап | Результат | Как проверить |
|---|---|---|
| 1. Фундамент | TS-кодовая база, IndexedDB, Capacitor, базовый UX | Данные из v0.1 мигрируют без потерь (тест на реальном дампе); уведомление из PoC срабатывает при закрытом приложении; редактирование/undo/тёмная тема работают; Vitest + Playwright зелёные |
| 2. ИИ-ядро | Прокси, LLM-категоризация, семантический поиск, чат | «Что я думал про X?» возвращает релевантные мысли из архива; при выключенном прокси приложение полнофункционально офлайн; затраты на тестовом периоде в рамках прогноза |
| 3. Слои состояния | Чек-ины, тренды, корреляции | Чек-ин занимает ≤10 секунд; после 2 недель данных экран «Состояние» показывает осмысленные тренды |
| 4. Планирование | Декомпозиция, приоритизация, weekly review | Мысль превращается в план из конкретных шагов одним тапом; review проходит за ≤5 минут |
| 5. Уникальные функции | «Эхо», «Анти-список», «Капсула» | «Эхо» находит реальные повторы и допускает ручную коррекцию; капсула «вскрывается» уведомлением в срок; ритуал анти-списка доводится до конца |
| 6. Публикация | Приложение в RuStore, работающая подписка | Установка из RuStore на чистое устройство; покупка и проверка подписки проходят; метрики поступают |

Этапы выполняются последовательно — каждый опирается на предыдущий: без фундамента нет места для эмбеддингов, без эмбеддингов нет «Эха», без уведомлений нет «Капсулы». Первый публичный релиз в RuStore собирается из результатов Этапов 1–5 (с тремя уникальными функциями) и закрывается Этапом 6.
